# Dictionary vs Sorted Array

C#/.NET 9, без Unity. Все команды выполняются из каталога `BenchmarkLab.sln`.
Нужны SDK .NET 9 и доступ к NuGet при первом восстановлении пакетов.

## Сборка и корректность

```powershell
dotnet restore
dotnet build -c Release --no-restore
dotnet test -c Release --no-build --no-restore
```

Альтернатива для проверки самих алгоритмов без тестового runner:

```powershell
dotnet run --project BenchmarkLab.Console -c Release --no-build -- validate
```

Проверки включают все размеры и распределения, сценарии, совпадение ссылок Entity,
граничные случаи и отсутствие аллокаций в прогретом поиске. Проверка матрицы
BenchmarkDotNet только перечисляет 432 комбинации, не запускает измерения.
Тест диагностики проверяет reflection и allocation-пробы модели размеров;
измерение удерживаемой памяти не выполняется.

## Измерения производительности (запускает пользователь)

```powershell
dotnet run --project BenchmarkLab.Console -c Release --no-build -- performance --profile Full --output artifacts/full
dotnet run --project BenchmarkLab.Console -c Release --no-build -- performance --profile Quick --output artifacts/quick
```

| Profile | LaunchCount | WarmupCount | IterationCount |
|---|---|---|---|
| Quick | 1 | 3 | 5 |
| Full (по умолчанию) | 3 | 5 | 20 |

Переопределение параметров и фильтр методов:

```powershell
dotnet run --project BenchmarkLab.Console -c Release --no-build -- performance --profile Quick --launches 1 --warmups 2 --iterations 8 --filter '*Binary*' --output artifacts/binary
```

Остальные аргументы передаются BenchmarkDotNet. Для полной матрицы используется
фильтр `*`. Не смешивайте настройки BDN jobs через дополнительные параметры с
профилями: экспорт рассчитан на один job на комбинацию.
Поиск проверяет 9 алгоритмов × 4 размера × 3 распределения × 4 сценария.
Quick охватывает ту же матрицу, но предназначен для предварительной оценки.
Каждый запуск перезаписывает результаты выбранного каталога; используйте разные
каталоги для разных машин, профилей и фильтров. При новом измерении устаревший
итоговый отчёт этого каталога удаляется.

`GlobalSetup` создаёт все данные, сортирует массив, подготавливает структуры и
проверяет результаты. Все алгоритмы используют одинаковые запросы; массив один.
Dictionary для поиска создаётся с начальной Capacity. Поиск не создаёт объектов,
результат пакета из 1024 запросов возвращается в BenchmarkDotNet как checksum.
Mean, Median, P95 и B/op нормализованы на один запрос, throughput = 1e9 / MeanNs.
Время включает цикл по запросам и получение checksum. P95 — процентиль средних
времён пакетов/итераций BDN, а не индивидуальных задержек. Сохраняются стандартные
настройки BDN обработки выбросов. Малые различия требуют анализа разброса.

Для `Array.BinarySearch<Entity>` заранее создаётся неизменяемый Entity-probe
для каждого запроса. Comparer сравнивает два Key обычным образом. Изменения
readonly-поля, boxing и аллокаций внутри поиска нет. Массив запросов не является
дополнительным индексом коллекции и не входит в её память.

## Данные и сценарии

Seed = 1729. Размеры: 10, 100, 10 000, 1 000 000. Уникальные ключи чётные:

- Sequential: 0, 2, 4, …; шаг 2 обеспечивает внутренние промахи.
- Random: случайные ключи из широкого диапазона [-1e9, 1e9).
- Clustered: примерно 90% кандидатов в [-4e6, 4e6), остальные в [2e8, 8e8).

Коллизии генератора повторяются до получения уникального ключа. Value генерируется
тем же seeded Random. Сохраняется существующий конструктор Entity(int), но
бенчмарк использует воспроизводимый Entity(int, int).

Hit выбирает разные ранги по всей коллекции. MissInside — отсутствующий нечётный
ключ между минимумом и максимумом. MissOutside — поровну минимум−1 и максимум+1.
Mixed: 512 Hit, 256 MissInside, 256 MissOutside. В каждом сценарии 1024 запроса,
детерминированно перемешанных; запросы повторяются при малом N. Данные и запросы
не моделируют все возможные production-нагрузки.

## Память (отдельно от поиска)

```powershell
dotnet run --project BenchmarkLab.Console -c Release --no-build -- memory --output artifacts/full
```

Выполняются 240 отдельных процессов: 4 размера × 3 распределения × 4 структуры ×
5 повторов. Структуры: Entity[], DictionaryPreallocated, DictionaryAutoGrow,
SortedDictionary. Вставка идёт в порядке сортировки; удаления не моделируются.
Все Entity внутри сравниваемых структур имеют одинаковые значения; процессы
изолированы, поэтому физическая идентичность объектов между процессами невозможна.
При совместном построении структуры используют исходные ссылки без копирования.

**Measured Memory** — оценка удерживаемой управляемой памяти по разности
`GC.GetTotalMemory(true)` после полных GC, не точный размер объекта и не working set.
Для небольших структур создаются независимые копии до примерно 8 MiB расчётной
Structure Memory. Массивы корней подготовлены до базовой линии. Structure исключает
Entity: они удерживаются до и после построения. Total включает новые Entity;
временные массивы источников освобождены перед финальным GC. Сохраняются медиана,
минимум, максимум и исходные повторы. Отрицательные измерения не обнуляются;
отношения с неположительными значениями отсутствуют.

**Estimated Memory** — отдельная аддитивная модель. Allocation-пробы текущего
runtime калибруют shallow-размеры объектов и массивов с заголовками/выравниванием.
Это не измерение удерживаемого графа. Dictionary = оболочка + buckets + entries;
Entity учитываются отдельно. Дерево = оболочка + TreeSet + принадлежащий ему
comparer + N узлов. Общие singleton-comparer исключены. Reflection обращается
к внутренним полям только в диагностике; несовместимый runtime даст ошибку.
Значения Capacity для дерева в CSV равны N как число узлов без резерва, в Markdown
показано N/A. UnusedCapacity для него — 0.

`BuildAllocatedBytes` — все аллокации построения структуры после прогрева, включая
промежуточные массивы AutoGrow, но без Entity. `EntityAllocatedBytes` измеряет
создание Entity отдельно. Генератор, подготовка запросов, JIT, native memory,
стек и harness не относятся к памяти структуры. Аллокации не равны retained memory.
Разность Measured и Estimated может отражать шум GC или ограничения модели;
для точного объяснения потребуется heap dump. KiB = 1024 байта.

## CSV, Markdown и графики

После обеих частей в одном каталоге:

```powershell
dotnet run --project BenchmarkLab.Console -c Release --no-build -- report --output artifacts/full
```

- `performance.csv`: Mean, Median, P95, op/s, B/op по каждому сценарию отдельно.
- `memory.csv`: Measured/Estimated Structure и Total, bytes/element, отношения к
  массиву, Capacity, резерв, buckets/entries и аллокации построения.
- `memory-samples.csv`: исходные повторы, включая число копий.
- JSON: машинные данные и фактически применённые параметры среды/профиля.
- `BenchmarkDotNet/`: исходные логи, стандартные результаты и описание CPU/среды.
- `BENCHMARK_RESULTS.md`: таблицы, сравнения и SVG-графики по распределениям и
  сценариям. Графики используют логарифмические оси; неположительные оценки
  памяти на них не показываются, но остаются в CSV.

Числа CSV записываются в invariant culture. Память массива не дублируется для
каждого алгоритма. Итоговый отчёт требует полных матриц и completion-маркеров;
частичный запуск/отсутствие файлов даёт `REPORT_INCOMPLETE.md` и код возврата 2.
Неизвестные B/op остаются пустыми, не заменяются вымышленным нулём.
До реальных измерений итогового отчёта и CSV с результатами нет.
